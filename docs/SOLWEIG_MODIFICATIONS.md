# What this repo changes in SOLWEIG-GPU

Everything we change relative to SOLWEIG-GPU v2.0.0: what, how, why, what it does to the outputs and how it was checked. Update it when anything is added. Last updated 6 Nov 2026.

The exact code differences are in `docs/patches/*.diff`, one per changed function, generated from the code by `scripts/export_patch_diffs.py`.

## Rules

- The installed package is never edited. Every change is applied at run time inside a context manager and undone when the block ends. Without these context managers SOLWEIG-GPU runs as released.
- A change that edits SOLWEIG's source (by compiling an edited copy of a function) first checks that the original is the one it was written for. The replacements check a SHA-256 fingerprint of the original function, the source-text patches check that each line they replace occurs exactly once. A mismatch raises an error. So a new SOLWEIG-GPU version fails loudly and has to be checked again.
- Every change states its effect on the outputs: bit-identical, equal within a stated tolerance, or a deliberate physics change. Only physics changes alter results, and they are only used in the experiments named below.
- The reference is the original code. It is deterministic (two runs give bit-identical outputs, checked 30 Oct), so every change can be compared with it exactly.
- After adding or editing a change, rerun `scripts/verify_fast.py` and the tests, together with the changes already there, not only on its own.

## Choices

- Keep the interface, change only the storage. A compact mask hands out what the original array would have: the same values in the same type (float32) for the indices SOLWEIG uses. Code written for the original behaves the same, including arithmetic that would go wrong with small integer types. The cost is converting the patch that is asked for, a few MB at a time.
- Check the assumption where the data come in, and fall back to the original if it fails. Compact storage needs the masks to be 0 or 1. That holds for every value in our three real tiles (about 2.75 billion values: Pacoima and Austin at 1000 x 1000, Pacoima at 2000 x 2000), but the shadow code can in principle produce a 2 (it computes `1 - (0 - 1)` in one branch). So it is checked once per tile, at load and per patch when the sky view factor is built. If it fails, the mask stays float32 like the original and a warning is raised. Not checking could give wrong results without notice, and stopping with an error would refuse inputs the original handles.
- Fail loudly rather than compute something different. Unsupported indexing raises, a changed SOLWEIG version raises, and TF32 is switched off rather than assumed off.
- Prefer bit-identical. Only C1 is not, and it is closer to the exact sums than the original (see the costs below).

## How it was checked

- **Unit tests** (`tests/`, CPU, synthetic tiles, run on every change). Hourly shadows and ground view factors bit-identical at 14 azimuths (exactly 0°, 45°, 90° ... and values a hair either side) and sun altitudes 0.5-80°, plus flat and building-free tiles. Sky within relative 1e-5 at six sun positions including night. Packed indexing at every byte boundary and over slices, `diffsh` on demand equal to the stored array, float32 fallback for a mask that is not 0/1. Compact `svf_calculator` equal to the original on all 19 outputs. Every patch restored afterwards.
- **C1-C3 on the GPU** (30 Oct, `scripts/verify_fast.py`, `figures/profile/verify_fast.json`). Four configurations: Pacoima summer, Pacoima winter (21 December, low sun), Austin (more trees, UTM 14N, Central time), Pacoima as four non-square 600-pixel tiles.

  | Check | C3 hourly shadows | C2 ground view factors | C1 sky |
  |---|---|---|---|
  | Every call during real runs, against the original on the same inputs | 93 of 93 bit-identical | 1,674 of 1,674 bit-identical | 168 calls, max relative difference 2.6e-6 (0.0017 W/m²) |
  | Sun sweep on real geometry (12 azimuths incl. branch boundaries, altitudes 0.5-89°, night for the sky) | 72 of 72 bit-identical | 12 of 12 bit-identical | 84 calls, max relative 2.1e-6 |

  End to end, all four configurations, all pixels and hours: shadow, Kup, Kdown and Lup bit-identical; Ldown within 0.0007 W/m², UTCI within 0.00011 °C, Tmrt within 0.00009 °C; missing values in the same places. Two runs of the fast path are bit-identical. Rerun with chunks of 8 on Pacoima summer and Austin: the same.
- **C4** (30 Oct, `scripts/verify_compact.py`). Pacoima summer, Austin and Pacoima as four 620-pixel tiles, uint8 and bit masks, each with the original and with C1-C3: 12 of 12 comparisons bit-identical on all seven outputs. After `PackedMask` was changed to return float32 slices: 8 of 8 again (`figures/profile/verify_compact.json`).
- **C5** (30 Oct, `scripts/verify_compact_svf.py`). The Pacoima sky view factor with the original code and with compact masks gives identical cache files, 19 of 19 arrays, values and types.
- **C6-C9, step by step** (3-4 Nov, `scripts/bench_steps.py`, `figures/profile/bench_steps.json` and `bench_steps_b.json`). Two sessions on a quiet machine on AC power. Each step's first run compared with the step before on all pixels and hours: C6, C7, C8 and both parts of C9 bit-identical in UTCI and Tmrt, C1 and the chunk change within 0.0001 °C as before. The sky view caches after C5, C6 and C7 are byte-identical to the original's (2 files and 15 zip members each).
- **2000 x 2000 tile** (4 Nov, `figures/profile/bigtile_compare_current.json`). The day with C1-C9 agrees with the original within 9.2e-5 °C, nowhere above 0.01 °C. With C1-C9 the sky view step and the day fit in 0.9 and 4.2 GiB of the 8 GB GPU; the original day needs 11.7 GiB.
- **Mask values.** Every value of the cached masks of the three real tiles is 0 or 1 (`scripts/check_mask_values.py`).
- **Memory** (`scripts/profile_memory.py`). C2 and C3 change neither allocated nor reserved memory. Each change reports its memory as well as its time.

## Costs and limits

1. **C1 is not bit-identical.** It sums the 153 patch contributions in chunks instead of one after another, and floating-point sums depend on order. UTCI and Tmrt differ from the original by up to about 0.0001 °C. Against a float64 reference on the same inputs (`scripts/sky_rounding_check.py`), the original's largest error is 6.2e-4 W/m² (mean 7.3e-5) and C1's 1.7e-4 W/m² (mean 1.6e-5), so C1 is 3.6-4.6 times closer to the exact sum. Making it bit-identical would mean summing in the original order again, which is what made it slow.
2. **Tied to v2.0.0.** All changes are fingerprinted to it and refuse to run on anything else. Every upstream release means checking again. Draft PR #137 (below) changes the code that C3, C5 and C7 touch.
3. **Patching at run time is not a long-term home.** It keeps the installed package untouched and every change switchable, but these belong upstream, as small pull requests with their tests.
4. **Narrow indexing.** `PackedMask` and `LazyDiffsh` support only the indexing v2.0.0 uses and raise for anything else, so code that uses the masks differently (a later SOLWEIG, a script calling `.sum()` on a mask) stops instead of computing something wrong. Since 30 Oct `PackedMask` returns float32 slices, the type of the original arrays. Before, it returned uint8, which is exact for every expression in v2.0.0 but would silently wrap `mask - 1` to 255. The `"uint8"` mode still returns bytes; use `"bits"`, the default.
5. **Not yet tested:** WBGT output, the shadow path without vegetation (`_13`, unchanged), CPU-only runs, data-centre GPUs (TF32 is forced off for them), real tiles above 1000 x 1000 other than the 2000 x 2000 test.
6. **One laptop.** All timings are from an RTX 4070 Laptop GPU under WSL2 (Windows driver 555.97, Intel CPU). Since 3-4 Nov each step is timed 5 times in each of two sessions (the sky view step 3 times), and the sessions agree within 4%. Earlier numbers were mostly single runs with about ±2 s noise. Speed-ups on other machines are estimates: C2, C3 and C7 remove CPU-GPU round trips, so their gain is about the number of syncs removed times the cost of one, and that cost depends on the CPU, the driver and the OS. The results should not depend on the machine, since the arithmetic is the same, but bit-identity has only been checked on this laptop.
7. **The stack is pinned by the environment, not by the fingerprints.** The fingerprints guard SOLWEIG-GPU's source only. PyTorch 2.5.1, CUDA 12.1 and the other libraries are pinned by `environment.lock.yml`; the NVIDIA driver is not pinned. Another PyTorch or driver could change kernels and with them the last bits of the results, in the original and the fast code alike. Rerun the GPU checks (`verify_fast.py`, `verify_compact*.py`, `verify_fast_sky_shadow.py`) on a new machine before trusting results.
8. **Licence.** The changes are derived from GPL-3.0 code, so this repo is GPL-3.0.

## Upstream

- **Latest version.** SOLWEIG-GPU 2.0.0 (PyPI, 17 Aug 2026) is the latest release (checked 9 Nov 2026). Commits on GitHub since then (the last on 19 Oct) only touch the README, the citation and comments. We found no speed or memory work in the official repository; the fork below has some.
- **Patch count.** `svf_calculator` generates azimuths for 149 of the 153 sky patches, because `int(360 / step)` truncates in float32 for four rings (confirmed 30 Oct, `scripts/check_patch_count.py`). All our sky view caches inherit this. C5 leaves that loop as it is, since fixing it changes results.
- **Draft PR #137, "Fix vegetation shadow patch generation"** (opened 5 Jul 2026, still a draft). It reports that the vegetation shadows inside the sky-patch masks (`shadow()`, called by `svf_calculator`) use UMEP's pre-2021 algorithm and over-cool tree shade compared with current UMEP-SOLWEIG (about twice the cooling over four times the pixels in their benchmark). It proposes the current UMEP algorithm, float64 ray angles for the zenith patch and versioned sky view caches. A fork that refers to it (iadicarlo, 8 Oct 2026) also reports the patch-count rounding above and Tmrt changes of up to 4 K locally once it is fixed. Our results inherit v2.0.0's behaviour under trees. If the PR is merged, C3, C5 and C7 refuse to run until checked again, and sky view caches have to be rebuilt.
- **What we measured about these fixes** (our runs, not the PR's benchmark). With settings matched to umep-core's SOLWEIG (anisotropic sky, 3% canopy transmissivity, the same rasters and forcing) on three synthetic single-tree scenes, v2.0.0 cools added trees within 5% of UMEP, slightly less, not twice as much (`scripts/umep_single_tree.py`, `figures/umep_single_tree.json`); the PR's benchmark may differ in setup. On the Pacoima tile (30 Jul 2019) the fork's full fix changes daytime outdoor Tmrt by -0.07 K on average and by up to 7.6 K at single pixels. Its parts: generating all 153 patches 0.17 K mean absolute (up to 7.4 K), float64 angles for the zenith patch +0.02 K (it raises the sky view factor by 0.011 everywhere, since in float32 the zenith patch shades itself), the current UMEP vegetation scheme -0.08 K (up to 6.6 K) (`scripts/eval_fork_fix.py`, `figures/profile/fork_fix_effect.json`).
- **Earlier speed work in that fork.** Besides the loop bound (C6, taken from it), commits 5932ef9 and 96e718e (Isma A. Di Carlo, 8 Oct 2026) move the per-step bookkeeping of both shadow loops to Python numbers, which removes a sync per step. That is the idea of C3 and C7. C3 was written on 30 Oct before we knew of the fork and C7 follows C3, but the fork did it first. We looked at its speed changes on 1 Nov.
- **Perez sky clearness** (found 4 Nov, not changed here). SOLWEIG-GPU's `Perez_v3`, like UMEP's SOLWEIG it is ported from (`Perez_v3_moved.py`), computes the sky clearness as `((Idh + Ibn) / (Idh + 1.041 z^3)) / (1 + 1.041 z^3)`. The published definition (Perez et al. 1990, Solar Energy 44:271, as in pvlib's `irradiance.perez`) is `((Idh + Ibn) / Idh + 1.041 z^3) / (1 + 1.041 z^3)`, with z the solar zenith in radians. At low sun the coded form puts clear skies into the most overcast clearness categories, and it causes two of the jumps in Tmrt against a radiation error (`scripts/radiation_perez.py`). With the published form, Tmrt on the heatwave morning of 6 Sep 2020 (08:00, Exposition Park) changes by -4.6 K on average and up to 28.6 K in single pixels, and by +0.6 to +0.8 K at 17-18 h on 30 Jul 2019; at midday by less than 0.1 K (`scripts/perez_formula_effect.py`). UMEP has both forms: its older shared copy (`umep/util/SEBESOLWEIGCommonFiles/Perez_v3.py`) uses the published one, the copy SOLWEIG uses (`umep/functions/SOLWEIGpython/Perez_v3_moved.py`) the other, so it looks like a slip when the file was moved. We checked against pvlib and Sandia's PV modelling reference, not the 1990 paper itself. This is a question for the UMEP and SOLWEIG-GPU maintainers; the repo keeps the code as it is, with `--perez published` in the scripts that test it.

## Reproducibility

- **Software:** `environment.yml` pins the main versions (Python 3.11, GDAL 3.13.3, NumPy 2.4.6, PyTorch 2.5.1 with CUDA 12.1, solweig-gpu 2.0.0, SALib 1.6.0, numba 0.68.1); `environment.lock.yml` is the full export.
- **Seeds:** Morris design 0 (`run_morris.py`), Monte Carlo 1 (`emulate.py`), forecast ensembles 0 (`run_la_forecast_error.py`).
- **Data:** `data/` is not in git. The SOLWEIG-GPU sample data is on Zenodo (21081622). For Los Angeles, retrieved 29-30 Oct 2026 from USGS 3DEP, the LA County DPW building outlines, Meta/WRI canopy height v1 (AWS), ESA WorldCover 2021, the Iowa Environmental Mesonet ASOS archive (KVNY) and Open-Meteo (ERA5). Live services can change, so `data_checksums.sha256` keeps SHA-256 checksums of every downloaded and derived file; the build scripts regenerate them.
- **Licence:** SOLWEIG-GPU is GPL-3.0. The patching modules contain short excerpts of its code (the text they search for) and the replacements are derived from it, so this repo is GPL-3.0 too.
